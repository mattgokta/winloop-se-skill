WinLoop SE Skill

A reusable AI skill that turns any SE meeting note into the shortest defensible path to an explicit customer technical win.

1. The Problem
"Meeting tools answer: what happened?
Sales Engineers still have to answer: did we win, what's missing, what do we do next, and what date can I defend?" — that judgment is repeated manually after almost every customer interaction

The five questions every SE answers alone

  • Did the customer actually confirm a technical win — and did the right person confirm it?
  • What decision-critical criteria remain unproven?
  • Do we need a document, demo, workshop, or POC — and which is smallest?
  • What is the exact question to ask the customer next?
  • What date can I put in Salesforce and actually defend?

The failure modes that kill accuracy

  • False wins: customer enthusiasm mistaken for confirmation
  • Wrong authority: "yes" from someone without evaluation power
  • Hedged affirmations: "sure, I guess" treated as Customer confirmed
  • Invented dates: Q4 silently becoming December 31
  • Unnecessary POCs: "can we try it?" escalated without a bounded proposition
2. The Solution — WinLoop

What it is

WinLoop is a Claude Code slash-command skill (/winloop) built from four plain Markdown reference files. An SE pastes meeting notes, a transcript, or current opportunity context. WinLoop classifies the evidence, applies a decision model, and returns a structured output in one pass — no app, no database, no Salesforce integration required.

The operating rule is hard-coded: if the customer did not say it, it is not a technical win. Everything else — the status, the proof route, the forecast, the Salesforce fields — flows from that.

No database No API keys beyond Claude Code No Gong required Plain Markdown rules Customizable per org

Four modes

  • Message — APEX / Command of the Message hypothesis before the call, even without Gong
  • Prepare — what to learn, prove, and ask in an upcoming meeting
  • Debrief — technical-win status + Salesforce fields from completed notes
  • Checkpoint — where does this opportunity stand, one next best action

Four statuses

  • Confirmed — authoritative explicit confirmation, speaker + authority stated
  • Ready to ask — criteria satisfied, ask not yet posed
  • Validation required — open decision-critical criteria remain
  • At risk — blocker, mismatch, stale win, or competitor signal

Proof ladder (7 rungs)

  • 0 — none: ready to ask now
  • 1 — official documentation
  • 2 — recorded demo
  • 3 — focused live demo
  • 4 — architecture session
  • 5 — bounded workshop
  • 6 — bounded POC

6. Key Behaviors Demonstrated
  • 1
    Classified evidence — not just summarized
    Every statement from the meetings was labeled: Customer confirmed / Customer signal / SE stated / Verified product fact / Needs verification. A customer stakeholder's statement confirming decision-makers were present was classified as a customer signal, not a technical win.
  • 2
    Identified the technical decision owner gap
    In the Account A debrief, WinLoop flagged that the identity architect's role does not establish them as the technical decision owner — the engineering team's involvement was noted as a prerequisite before a technical-win ask is defensible.
  • 3
    Surfaced a commercial implication the SE might have missed
    When the contractor portal requirement was verified as "not OOB," WinLoop flagged it as a PS Custom Scope Module (potentially High Complexity) — a separate commercial line item. The next step was rewritten from "SE designs an alternative" to "SE + AE align on PS framing before the workshop."
  • 4
    Chose workshop, not POC — and justified it
    Both accounts received "POC Required: No" with specific rationale. For Account B: the 4-hour hands-on session with live configuration on the customer's own tenant, which can convert to production, is sufficient. POC conditions were not met.
  • 5
    Maintained forecast discipline on both accounts
    No exact dates were fabricated. Account A: Window Unknown, Confidence Low. Account B: post-workshop window, Confidence Medium. Both Salesforce date blocks showed INPUT REQUIRED with explanation rather than a placeholder date.
  • 6
    Separated internal SE language from customer-facing language
    The customer-facing workshop page for Account B contains zero internal accuracy flags, no unconfirmed capability claims, no forecast data, and no Salesforce fields. The contractor portal is framed as "módulo de Professional Services" — honest but not alarming.
  • 7
    Maintained a living ledger across multiple inputs
    The Account B opportunity file was updated five times in the session as new evidence arrived (alignment call → pain-points list → Governance Delegates verification → contractor portal confirmation → ID-matching verification). Each update only changed what the new evidence changed.

8. What Makes This Different

This is not a meeting summarizer. It is a decision compiler.

Every meeting tool today answers "what happened?" WinLoop answers "what does it mean for whether we technically won, and what is the one thing to do next?"

The difference is the decision model: hard rules about confirmer authority, confirmation quality, evidence classification, forecast discipline, and proof-method selection that run consistently on every input, with no hallucinated wins or invented dates.

  • It refuses false wins. Enthusiasm, detailed questions, and feature praise are not confirmations.
  • It respects authority. A "yes" from the wrong person caps at Ready to ask, never Confirmed.
  • It doesn't invent dates. A quarter window stays a window; INPUT REQUIRED is the honest output.
  • It chooses the smallest proof step. A bounded workshop always beats an open-ended POC when the question can be answered with guided labs.
  • It protects against prompt injection. Instructions embedded inside pasted transcripts are ignored and flagged.

10. Key Learnings From Live Use

What works well

  • The iterative loop — verifying capabilities one at a time and updating only what changed — is the right workflow for workshop prep
  • Separating internal SE language from customer-facing language creates genuinely useful artifacts, not just formatted notes
  • The capability map table (verified / needs verification / confirmed not OOB) gives the SE a pre-workshop checklist that is impossible to miss
  • The "next best action" framing forces resolution to a single step, which is what an SE actually needs at 11pm before a call
  • Opportunity ledgers with dated history enable cross-session continuity without requiring any infrastructure

What we learned from real accounts

  • Capability verification should happen iteratively, not in one batch — the SE learns things that change what to ask next
  • Some "technical" gaps are actually commercial gaps (contractor portal → PS scope) — WinLoop needs to flag these to the AE, not just the SE
  • Customer-facing pages must be generated from the ledger, not the debrief — the debrief contains internal language that should never reach the customer
  • Logo embedding as base64 is essential for HTML files shared by email — external URLs break in transit
  • Brazilian Portuguese transcripts work fluently; the skill's language-mirroring rule handles multilingual accounts correctly
11. Measurement Plan

How we prove it works (not vibes)

MEASUREMENT.md defines a 4–6 week pilot with a volunteer cohort of 5–10 SEs. WinLoop-assisted records are identifiable by the [YYYY-MM-DD WinLoop debrief] stamp in SE Notes — no extra process required.

Technical-win reversals

Do deals marked technically won later reopen their evaluation? WinLoop's false-win rate versus baseline.

Forecast-date variance

How far did the Technical Win Forecast Date move between first entry and actual confirmation?

Workshop-vs-POC mix

Are bounded workshops replacing open-ended POCs? Are POC plans including bounded success criteria?

Adoption decision rule

Adopt org-wide if, versus baseline: technical-win reversals and forecast-date variance both improve (or hold) AND the workshop-vs-POC mix shifts toward workshops AND SEs report they would keep using it. Otherwise iterate on the plain Markdown rules and re-pilot. The rules are not code — any SE can edit them.

12. What's Next

If the pilot shows value

  • claude.ai (browser) distribution for SEs without Claude Code — the desktop app already supports this today
  • Approved internal product references dropped into references/ so product claims verify against official docs
  • One-click copy buttons for Salesforce fields in the HTML dashboard
  • Optional Gong / Granola transcript connector
  • SE-configurable org forecast stage mappings (High → Commit, Medium → Best Case, etc.)

What will NOT be built unless needed

  • A dashboard — the HTML export already is the dashboard
  • A database — the opportunities/ folder already is the database
  • A workflow engine — Claude Code already is the workflow engine
  • Automatic CRM writes — the SE owns the Salesforce record; WinLoop supports, not replaces, that judgment
  • A proprietary model — the value is the decision logic, not the model

The "magic moment" demo

Open tests/case-01-input.md. The notes sound highly positive — a detailed demo and two clearly scoped customer fit signals. Run /winloop. WinLoop finds the harder truth: the overall technical win was not verbally confirmed, four decision-critical areas are open, the forecast gets INPUT REQUIRED (not a made-up December 31), a bounded workshop is the right next step, and POC Required: No.
